# 「部分人卡、杯赛和交易特别卡、换浏览器也卡」：排查与修复

2026-10-08。线上只读采集（Railway HTTP / 应用 / Postgres 日志，`/api/admin/perf`、`/api/admin/db`），数据见 [summary.json](summary.json)（只有按时间、路径的汇总，不含 IP 和 UA）。

## 结论

不是浏览器、不是某些账号慢，是**全站一起停顿**，恰好撞上正在玩杯赛、交易的人。

- 部署 0d3a7966 之后 8 小时（05:45–14:07 UTC），≥1 秒的 API 慢请求 1,193 条，来自 500 个不同客户端；**965 条（81%）落在几次全站停顿里**。停顿之外只有零散的 1–2 秒，没有哪个客户端持续慢。
- 「部分人流畅」：电竞经理在浏览器本地模拟，几乎不请求服务器；开瓦包的杯赛、交易、开包每一步都要服务器。停顿时只有后者卡。换浏览器当然没用。
- 进程本身没问题：事件循环最大延迟 118 ms，比赛 worker 无积压，交互池平时等待 p95 为 0。

## 三次大停顿

Railway HTTP 日志的时间戳是**请求结束**时刻（封号→刷新名单的相邻两条可证），下面按开始时间算。

| 开始（UTC / 北京） | 慢请求 | 最长 | 原因 |
| --- | ---: | ---: | --- |
| 10:51:43 / 18:51 | 370 | 45.7 s | **Railway 每日备份**（pgBackRest）：先要一次立即检查点，再 57 秒读走 3.5 GB |
| 14:06:43 / 22:06 | 217 | 36.2 s | **后台统计面板**：`/api/stats` 从 14:06:43 跑到 14:07:19 |
| 13:30:12 / 21:30 | ~170 | 75.2 s | 未查明：应用、Postgres、后台操作都没有对应记录 |

另有每 10 分钟 :x5:26 的 1–3 秒小簇（上一轮已知的请求回复压缩与小时维护）、11:16 的 4 秒小簇（card_requests 自动清理）。

### 备份：每天北京时间 18:4x–18:5x

Postgres 日志里的 7 次备份：10-02 10:42:28 起，每天比前一天晚约 1.5 分钟（上次结束后约 24 小时再跑），10-08 已到 10:51:41，持续 39–69 秒。正落在晚高峰。线上盘慢（上一轮实测约为本机的 1/70），备份读盘时 `market/history` 先撞 15 秒语句超时，四条交互连接被占满，`act`/`save` 等 30 秒拿不到连接后失败（日志 10:52:29–31）。

代码改不了备份时间，见文末「需要所有者决定」。

### 统计面板：一次打开 = 6 路全表扫描

`overview()` 是二十多个直接扫 events（300 万行、堆 774 MB）的聚合，其中留存、日活两条连时间范围都没有。原实现 `Promise.all` 在两条统计连接上同时跑，Postgres 默认又给每条查询加 2 个并行 worker（本机 73 MB 的表就已经 `Workers Launched: 2`），即约 6 个进程同时顺序读。`/api/admin/db` 的 `tempMb` 累计 4.4 GB，也是这类排序落盘。两条统计连接都被占住，`/api/e` 145 条排队到 34 秒。

### 两个放大器

停顿本身几十秒，但有两处读在停顿里把它拉长、并占住玩家的连接：

1. **天梯榜回退扫描**（`cards-api.js` `topRows`）：投影读（自己名次的 count）一超时，就改走 `rankedRows`——解压每份存档的全表扫描（上一轮测 95.7 万页），在交互池上。日志 10:52:09、10:52:25 两次 `board from projection failed, scanning … statement timeout`。`/api/card/top` 慢请求中位数 15 秒。
2. **成交记录**（`market-api.js` `history`）：每点开一张卡都现算该卡全部成交的均价、中位数，热门卡上千笔随机读；停顿时是最先超时的语句（Postgres 日志 10:51:59–10:52:20 连续 4 条）。

## 改动

| 处 | 改成 |
| --- | --- |
| `server.js` `/api/stats` | 一个只读事务、**一条连接**、`max_parallel_workers_per_gather = 0`；结果留 30 分钟，过期先回旧的、后台重建（单飞）；`?fresh=1` 立即重建，60 秒内只建一次 |
| `dashboard.js` | 状态栏写「统计于 HH:MM」；加「重新统计」按钮 |
| `cards-api.js` `topRows` | 超时（57014）、锁超时（55P03）、等不到连接：给最近建好的那一百，没有就报错；**只有投影本身出错才退回扫描** |
| `market-api.js` `history` | 每张卡每个等级的统计留 60 秒，同时来的人只查一次，查失败不缓存；挂牌手数（按挂牌走）照旧现查 |
| `src/data/changelog.ts` | 玩家可见的一条 |

## 验证

- 新检查 `scripts/check_stall_reads.ts`（已入常规审计）：成交记录 60 秒内不重查、8 人并发只查 1 次、失败不缓存、过期后重查并算进新成交；天梯榜在投影读超时时给缓存且**不扫描**，冷启动超时报错也不扫描，投影真坏了仍退回扫描。拿回旧的 `cards-api.js`、`market-api.js` 跑：8 项失败。
- 本机 PostgreSQL 18.6 一次性实例、30 万条事件，跑真正的 `server.js`：首次 1.6 s 构建，再请求 1 ms；构建期间该库每 50 ms 采样，**活动连接最多 1、并行 worker 0**；页面上「重新统计」过 60 秒确实重建，控制台无报错。
- 原有相关检查全部通过：`check_market_history`、`check_account_projection`、`check_cards_api`、`check_rollup`、`check_pool_deadlock`、`check_last_season`；`npm run typecheck`、`npm run audit`。

本机盘快、表小，**不能用来证明线上停顿缩短了多少**。上线后按本文同法采 ≥1 秒慢样本：后台打开面板时不应再出现上百条的簇；备份那一分钟应仍有（这一项没修），但 `top` 不再出现十几秒的长尾、日志不再有 `board from projection failed, scanning … timeout`。

## 需要所有者决定（代码改不了）

1. **备份时间**：Railway 托管的每日备份现在落在北京时间约 18:52，且每天晚 1.5 分钟、会一路漂过整个晚高峰。可在 Railway 的 Postgres 服务里看备份设置能否改到凌晨（如北京时间 04:00–06:00）；若时间不可选，可在目标时刻手动触发一次，看后续是否以它为基准（未验证）。
2. **events 表体量**：300 万行、1.8 GB，是备份和面板读量的大头。保留行数是 `ANALYTICS_MAX_ROWS`，降到 100–150 万能明显缩短两者，但会少看更早的原始事件（汇总表不受影响）。
3. **`shared_buffers` 128 MB**（上一轮已提）：调到容器内存约 1/4，需要重启数据库。
