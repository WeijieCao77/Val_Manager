# Claude Code 实施复核

日期：2026-10-05。对象：当前工作区未提交实现，以 git HEAD 与前次检查记录区分原有改动。没有修改业务实现或生产数据库。本次新增复核文档、复现程序和证据文件。

结论：优化方向成立，部分收益可直接验证；发现 3 个需要修复的边界问题，暂不建议把这一版作为已完成验收的版本发布。

## 需要修复的问题

### 1. [P1] 经理推进中途离开，已完成的模拟日没有进入保存流程

位置：`src/ui/Dashboard.tsx:149–152、163–170`；`src/ManagerGame.tsx:222–229`。

新 runTurn 在 advanceDay 修改 game 后，通过 breathe 让出执行。用户此时使用浏览器返回键切走模式，Dashboard/ManagerGame 会卸载；root 的 inert 和遮罩无法阻止浏览器导航。breathe 返回 false，runTurn 提前 return，跳过 handleReports，而 commit 在 handleReports 里。父组件的卸载/pagehide 保存只有 saveTimer 非空才执行，已保存完上次操作时 timer 通常为空，因此本次已完成的日程变化没有保存。原同步推进中不存在这个让导航插入执行的窗口。

复现：直接从当前 Dashboard TSX AST 提取实际 runTurn 初始化函数，转译执行；模拟一个耗时 60 ms 的完整日，在第一次让出时卸载，并调用父组件相同的 flush 条件。结果 `day:10→11、commits:0、saveCalls:0`。这是实际回调逻辑的隔离验证，不是完整浏览器端到端验证。

建议：明确记录推进中“状态已变更”；每个安全日边界更新父级 dirty/检查点。中断路径也需保存最后完整状态，或回滚到推进前快照。卸载后不再更新页面状态，但不能跳过数据提交。另外取消尚未开始的 10 ms timer，避免组件离开后又推进一天。补浏览器返回、刷新、后台恢复与退出模式测试。

### 2. [P1] 投影异常被吞掉后，读者永久信任旧投影

位置：`account-projection.js:145–150`；`cards-api.js:1044–1054`。

account_project_v1 把实时更新异常捕获为 warning，保留旧投影并允许账号提交。这样保护了资产动作，但没有记录脏账号或失效状态。projectionComplete 只检查触发器存在和全局回填完成标记；API 一旦 projReady=true 甚至不再检查。旧投影的查询仍正常成功，所以“查询报错就回退旧扫描”无法救这个场景。

复现沿用提交测试中的临时 CHECK 约束故障注入方法：先完成回填，再让 account_rivals 的写入抛错，同时把账号积分从 7 改到 5000、suspect 改为 true。恢复约束后不再写账号。结果账号 state 已更新、suspect=true，但投影仍 ready=true，boardTop 继续显示 7 分，并且这个应排除账号仍出现在 rivalSample。其后没有相关 state/suspect 写入，就没有修复路径。seen 更新也不会触发该投影。

建议：异常时登记可持久恢复的脏账号/版本，后台重建并验证；读者对脏行跳过或回退真相源。可以保持资产写入成功，但不能保持“投影始终正确”的就绪承诺。投影加 source_rev，并保证过期状态有可观察、可修复路径。现有测试只检查“下一次写入能补正”，漏掉了“玩家不再写入时怎么办”。

### 3. [P2] 插入型回填保护不了已被新状态删除的投影

位置：`account-projection.js:95–98、129–132、204–205`。

`ON CONFLICT DO NOTHING` 只保护已经存在的新行。如果回填语句拿到旧账号快照后，另一事务清空阵容或移除某个 ladder，新触发器会删掉对应投影；回填再插入时没有唯一键冲突，于是旧有效阵容/旧排名被复活。该回填语句没有先锁账号并读取最新状态，也没有 source_rev、删除墓碑或完成后的对账。

复现：使用真实 account_project_v1。先有合法五人和排名，再更新 state 为无 squad/ladder，确认投影已删除；向回填函数注入更新前快照（与现有“旧快照不会覆盖新行”的测试同类手法）。结果旧排名与旧阵容重新出现。**本次证明的是旧快照处理错误；未执行真实 PostgreSQL 双事务交错，因此不把它描述为已复现生产并发事故。** 在 PG 的并发快照下存在对应窗口，需补真实 PG 测试。

建议：对每个账号按一致顺序先取得行锁，再读取和投影当前 state，或使用版本/墓碑防止旧状态复活；完成前验证覆盖与版本一致。不要仅以“没有可回填 ID”写完成标记。补新写入删行、部分 league 删除、删除后再创建与两实例回填测试。

## 与原方案相比尚未完成

- 阶段 A 的线上分段基线、序列化/返回字节、客户端解析/保存耗时和峰值成功率还没新增；现有 perf 指标不等于整条链路。
- 增量响应、账号资产拆表、IndexedDB、长市场窗口化和 CardCtx 细分没有实施；它们可以后续做，无需为本次发布一次做完，但应标明完成范围。
- rivalSample 仍对所有非 suspect 小表行做 `row_number() ... order by random()`；消除了大 JSON 扫描，但不是按段位/评分的有界索引抽样。实际表规模大时排序成本仍需评估。
- 触发器在每次 state 写入时投影多个 league 和阵容，有相同值免更新，但规则提取与 FK/投影访问仍有成本。必须做同环境 A/B 测量读收益与写增量，不能只看前 100 的 EXPLAIN。
- 本人精确名次仍用 count 计算前方账号；低排名账号查询代价随规模增长，需放进压测。
- 未新增真实 PG 双事务测试或包含榜单、真实大存档、赛事、清理重叠的混合负载；新增 check_account_projection 未出现在 audit-checks.json 的常规测试清单中。
- 更新日志“推进时页面不再卡住”“切走或关闭页面前会先存好”表述过强。当前仍有单日主线程长任务和上述未保存窗口，建议改为准确的已实现行为，实机验收后再描述体验效果。
