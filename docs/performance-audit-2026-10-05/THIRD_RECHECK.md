## [P2] 旧保存冲突回包仍能覆盖更新阵容并重新保存

位置：`src/engine/account.ts:658–662`。

`absorb` 在第 196 行拒绝低于当前 rev 的回包并返回 null。但“另一个设备的阵容”分支忽略返回值，仍执行 `mergeClientFields(state, server)`、标记已同步、写镜像及发出设备冲突提示。版本检查因而没有保护这条合并路径。

复现使用真实客户端 account 模块、真实 API 路由和独立内存 PGlite：

1. 当前客户端保存 A；另一设备保存 B，使当前客户端的版本落后。
2. 当前客户端发送保存 A，服务器返回冲突及 B；测试只延迟这个回包，服务器已经处理完请求。
3. 回包尚未到达时，当前客户端切换 C 并排队保存；同时发起携带 C 的开包操作。操作成功，客户端和服务端都成为 C，客户端拿到更高版本。
4. 释放第 2 步的旧冲突回包。`absorb` 拒绝旧版本，但随后的无条件合并仍把画面改成 B。
5. 已排队的保存随后携带被改回的 B，服务端也永久回到 B。

两次独立运行均复现，客户端已知版本未倒退，但画面和数据库阵容均倒退。现有同步脚本分别覆盖了其他设备冲突与旧操作回包，尚未覆盖二者组合的回包交错。

修复建议：在处理冲突回包前先排除过期版本；被拒绝的回包不能改变客户端字段、同步标记、镜像或触发设备冲突通知。保留/续发当前待保存编辑，并对所有响应分支统一应用版本规则，包括 lean 成功回包。只在 `absorb` 接受当前响应后再执行相应合并；同时避免吞掉此期间排队的保存。

复现：[third-recheck-squad.mts](third-recheck-squad.mts)；输出：[third-recheck-results.json](third-recheck-results.json)。运行：

```sh
node --import tsx docs/performance-audit-2026-10-05/third-recheck-squad.mts
```

当前应出现两条 FAIL（画面保持 C、服务端保持 C），退出码 1；修复后两条应通过。
