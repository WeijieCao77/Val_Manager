## 一、当前版本公告、赛段环境和战术建议

已知现状：`src/engine/season.ts` 中的 `applyPatch` 会修改 `state.patch`，并写入加强/削弱新闻；`settleCompetition` 在国际赛结束结算后触发更新，Champions 后是休赛期大改。`src/engine/comp.ts` 和比赛逻辑已经使用版本信息。因此不是“还没有版本机制”，主要问题是缺少持续可查且能指导决策的展示。

实施要求：

1. 在主界面提供明显的“当前版本”入口，并在战术页显示当前版本摘要；不能只能翻新闻找到。
2. 展示当前版本名称、生效游戏日期、影响哪个后续阶段、加强/削弱的英雄，以及具体影响。重复的“赛中调整”应通过日期或版本 ID 区分。
3. 从现有真实版本权重、地图池及打法模型推导“当前更适合什么阵容/打法”；明确区分版本优势、地图适配与本队熟练度。没有数据支持某种打法时，不要编造统一答案。
4. 显示本队当前阵容哪些位置或英雄受益/受损，以及可执行建议，例如调整某图英雄或安排未满熟练度英雄训练。不要自动覆盖玩家战术。
5. 版本生效时有一次可见通知，之后仍能查看当前公告与最近历史。所有文案与引擎实际变化一致，并说明这是游戏存档内版本，不冒充 Riot 真实公告。
6. 默认保留目前“国际赛结束后生效”的节奏，清楚写出影响之后的比赛；避免误显示成刚结束的赛事使用了这个新版本。

验收：跨国际赛结算、赛年切换、连续推进和读档后，当前版本正确、公告不重复；本队建议确实基于同一份版本数据。

## 二、选手生日变成可参与的事件

已知现状：`src/engine/life.ts` 的生日逻辑会写提示并自动增加士气，没有庆祝选择；其中使用固定年份换算生日，要特别核对与当前赛年日历是否一致。

实施要求：

1. 为本队有已知生日的选手生成可处理的生日事件，在主界面待办/日程/选手详情提供入口。
2. 提供有明确差异的选择：送祝福、送小礼物、组织简短庆祝、暂不处理。每项写清实际成本、付款来源、时间/行动点与效果；免费祝福也应有用途。
3. 结果作用于已有的士气、对经理信任、关系等适当指标，并有选择后的反馈和事件记录。协调原有自动士气收益，避免重复叠加；生日不直接大幅增加枪法等永久竞技属性。
4. 小礼物可由经理个人钱包支付；团队活动若走俱乐部经费，明确标记并通过俱乐部财务流程。不能混用账户。
5. 每位选手每个游戏年只处理一次；允许合理的处理时间窗，使“推进一周/到下一场比赛”不会直接错过。记录待处理、已处理、已过期状态。
6. 修正真实日期、闰年、2月29日和年龄显示的一致性。未知生日不编造具体生日；转会或离队后不能继续对已失效的本队事件支付。

验收：逐日推进与跨周推进都能触发；同生日多人可分别处理；反复点击和存读档不重复扣费或发效果。

## 三、修复训练自动推荐，并说明推荐理由

用户复现描述：“枪法已经练满，但点自动推荐仍然推荐练枪法。”

已知现状：`src/engine/training.ts` 的 `recommendedTrainingFocus` 已检查潜力、疲劳、指挥身份和属性 `<97`；`src/ui/Training.tsx` 的 `autoFocus` 还检查伤病。因此不要假定只缺少一个 `>=99` 判断，先找到用户实际走到的推荐入口和训练结算路径。若无法复现，要如实说明，并构造相关边界场景验证。

实施要求：

1. 排查所有“推荐/自动分配”入口及真正的收益函数：属性训练、团队训练、英雄熟练度等是否有各自不一致的规则。
2. 区分属性已满、成长进度条满、总评触及潜力、英雄熟练度满等不同情况。让推荐与真实上限、可成长条件、结算规则共用判断，不再散落互相矛盾的阈值。
3. 排除没有实际成长空间的项目，再考虑位置权重、短板、疲劳、伤病和可执行条件。只在本来能读取这些状态的训练流程中加入版本和地图需求，不强行重写所有推荐系统。
4. 全部达到可成长上限或需要恢复时，推荐休息/恢复或已有且适用的其他项目，并解释原因，不能回退到固定推荐枪法。
5. 给出简短理由，例如“枪法已达上限，改练当前可提升的意识”“疲劳偏高，建议休息”；涉及保持状态而非成长时，明确写出区别。
6. 保留手动选择；不能因为有自动推荐就在推进日期时悄悄覆盖手动计划。已共用该算法的 AI 训练也要回归验证。

验收必须覆盖：枪法已满但其他属性可练、全部属性无成长空间、潜力已满、疲劳、伤病、不同位置、非指挥选手、英雄熟练度100、旧存档缺省字段，以及自动与手动计划的关系。

## 四、经理年龄、个人钱包与生活状态

已知现状：`src/engine/manager.ts` 有经理年龄与技能，`src/ui/Career.tsx` 显示年龄与合同；`src/engine/season.ts` 在赛季/结局结算时把经理工资计入 `tally.earned`。这不是一个可消费的钱包，也不能未经核对直接把统计累计收入当余额。现有成长速度还与初始年龄有关，年龄变化和成长速度是否重新计算要明确，不要暗中修改出生背景提供的初始数值。

实施要求：

1. 经理年龄随游戏时间增长，使用与选手和日历一致的时间基准；优先采用创建时年龄+起始日期推导，或统一的生日规则，避免年末和生日各加一次。旧存档不能每读一次就加岁数；没有依据不要编造精确生日。
2. 新增个人钱包与简明收支记录，严格区别俱乐部预算、个人可用余额、生涯累计收入。
3. 工资要定期进入个人钱包。优先考虑按游戏月结算，让玩家赛季中可以消费；实现前统一原有年薪统计、赛末、五年结局、终局和换工作路径，防止月薪与年薪重复发放或重复记收入。
4. 合同中途变更、换队、失业和跨年要有一致的计薪规则。旧档迁移明确哪些已结算收入可以转入余额、哪些历史无法恢复；迁移只能执行一次，不能凭空补发多年的工资。
5. 首版实现“饱腹”和“心情”两个个人状态即可，均用0–100整数显示。饱腹100表示吃饱，0表示饥饿，避免把“饥饿值满”解释成最饿。状态随游戏日期变化，不随现实时间或浏览器开着的时长变化。
6. 提供可购买餐食、休息和娱乐活动的真实入口，可放在“经理生活”页或职业页；包括低成本餐食、较好的餐食、免费休息、付费娱乐等。价格、恢复量、冷却和使用条件都要显示并实际生效。
7. 支持玩家主动把饱腹维持在满值附近；可提供玩家主动开启的自动补给/连续安排，并有明确个人预算上限及余额不足提示。正常推进一周不能要求点七次吃饭，也不能把状态在后台突然扣空。
8. 状态需要有轻量的实际作用，例如对经理某些工作效率或互动结果的有限修正。挑选少数现有机制接入、统一计算并给出说明；不要用购买食物直接大幅提高选手战力，也不要要求状态100才允许比赛。
9. 数值先算再定：基于当前最低/常见经理薪资，验证基础饮食可负担、娱乐有可选价值、低余额仍有恢复办法、重复消费不能无限叠加状态或刷收入。使用明确边界和冷却，不引入饥饿死亡或新的生涯强制失败机制。

验收：按日/按周推进一致、同一日重复打开页面不扣状态、工资不重发、余额不为负、失业不发旧工资、自动补给遵守预算、读取旧档和跨赛年不会损坏生涯收入与结局统计。

## 五、更衣室争执变成经理可以处理的事件

已知现状：`src/engine/bonds.ts` 已有赛后争执、双方关系下降、士气变化和每周持续不和；`src/ui/Squad.tsx` 有关系矩阵；双排训练也能改善关系。已有机制要保留并接入，不要另建一套与关系值脱节的“冲突数值”。

实施要求：

1. 争执发生时保存可处理事件，包含事件ID、发生时间、涉及选手、可验证的比赛背景、严重程度和状态。不能靠解析新闻文字推导待办。
2. 主界面和更衣室显示待处理事件，并支持私下谈话、组织调解、安排现有双排协同训练、让某人暂时替补冷静、暂不介入等不同处理方式。
3. 明确每项成本、冷却、时间和影响范围；处理结果由现有关系、信任、经理更衣室能力等相关数据决定。随机结果使用游戏内可复现的随机状态，不能刷新就换结果。
4. 调解不必次次成功；处罚也不能稳定增加所有人的好感。影响要落到实际的关系、士气、信任、不满等系统，并展示结果与后续状态，不能点完只弹一句话。
5. “暂时替补”必须真的改变下一场可用的首发安排，接入当前阵容选择、自动排阵与首发承诺机制。给出期限、恢复入口和替代人选；没有合法替代者时说明原因，不能制造少于五人的阵容或让自动排阵立刻把受处罚者放回去。
6. 避免任意认定争执一方有罪：显示的是本存档模拟事件及其背景，不编造现实人物私生活。允许经理自己选处理对象，并承担相应管理后果。
7. 同一选手对的持续矛盾不要每天生成重复待办；关系未修复时保留持续状态。转会、离队或退役后关闭失效事件。忽略事件可以有后续影响，但不要无限刷屏。
8. 复用现有行动点。合理消耗谈话/活动行动点，阵容调整本身继续遵守现有免费原则，不让玩家为了省行动点被迫上不合适的阵容。

验收：调解真实改变关系；双排安排真正进入训练；暂时替补跨推进与读档仍有效且能恢复；重复处理不刷效果；离队、没有替补、换经理、自动排阵都有正确结果。
