# 卡顿修复：判断与改动

2026-10-06。在 [REPORT.md](REPORT.md) 和 [FIX_REVIEW.md](FIX_REVIEW.md) 之上，补充自己的判断、实测和对复核两项 P2 的处理。

## 判断：两种周期，都是数据库层面的全站停顿

把 1,392 条慢样本按时间聚成簇（≥4 条、间隔 ≤3 秒）后，有两种节律：

- **每小时 :36**（统计维护）：与 REPORT 一致。
- **每十分钟 :x7**：04:16:58 → 04:26:59 → 04:37:01 → … → 06:47:03，几乎不漂移。REPORT 没有单列这一项。

同一簇里统计池的 `/api/e`、主池的 `save`/`act`、市场 `browse` 在同一百毫秒内一起返回；而 `/api/admin/perf` 显示进程启动 13.6 小时以来事件循环最大延迟只有 178 ms（直方图未重置）。所以不是 Node 进程卡住，而是数据库让所有连接一起等。日志里「market: settling 0 took 7353 ms」（结算 0 条用了 7 秒）也说明维护期间 bg 连接上的普通查询一样被拖住。

十分钟节律对应 `sweepRequests`：`sweptAt` 在开始时记下，所以几乎不漂移；上赛季榜缓存在构建结束时记时间，会随构建耗时漂移，对不上。

## 实测：本机 PG 18、128 MB shared_buffers、生产规模表

`events` 300 万行（堆 808 MB，线上 774 MB），`card_requests` 82 万行，`card_accounts` 6.8 万行。`EXPLAIN (ANALYZE, BUFFERS)`：

| 语句 | 频率 | 触及页 | 本机 |
| --- | --- | --- | --- |
| 按天龄删（REPORT 的怀疑之一） | 每小时 | 200 | 0.03 ms，有 `ts` 索引，**不是问题** |
| 行数上限 `offset 3,000,000` | 每小时 | 8,169；表里有 41.5 万死行时 21,083，**43.9 万次回表**、弄脏 7,182 页 | 0.5 s |
| 每批 5 万行删除（从 id 最小处起） | 每小时 | 死行多时 15,097，**40 万次回表**、弄脏 12,974 页 | 0.19 s |
| `sweepRequests` 压缩回复 | **每 10 分钟** | 全表顺扫 22,547 页，逐行过滤 81.8 万行；和删除并行，占满统计池两条连接 | 0.19 s |
| 上赛季榜 | 每 10 分钟/每个联赛 | **957k**（每行把整份存档解压 5 次） | 2.3 s |
| 预测榜 | 每 5 分钟 | 267k | 0.7 s |

线上 `events` 有 39.3 万死行、上次 autovacuum 是 10-05 13:08，正是“死行多”那一列的情形。本机是快 SSD 加热缓存，绝对时间不能直接对应线上；页数就是线上要做的读写量。

## 改动

1. **请求回复压缩**（`cards-api.js` `sweepRequests`）：新表 `card_request_marks` 存游标，按 `at` 索引从游标往前走，一条语句、一次最多 5 万行；正常一次只处理新越过 6 小时线的约 2,000 行。本机：追赶期每次 40 ms，稳态 31 ms，追完后 6 小时以前未压缩的行为 0。超过 1 秒才打日志。
2. **小时清理**（`stats.js` `prune`，`server.js` 传 `pruneMemo`）：一次精确走表后，memo 记住 floor/top/rows；之后每小时只数新增、从 floor 往上删（不再爬死行）。每天、按天龄删过行、或这次没删完时重新走表。本机老化表：全量 1,123–1,610 ms，增量 **44–73 ms**，每次删完正好等于上限。维护每小时打一行耗时。
3. **杯赛报名/退出**（`opencup-api.js`、`teamcup-api.js`）：改在主池的短事务里，`lock_timeout 3s`；碰到开赛持锁则回「这一场正在开赛」。同一行锁、容量、重复报名规则不变。
4. **上赛季榜 / 预测榜**：缓存 6 小时 / 30 分钟，到期先回旧榜、后台单飞重建；SQL 每行只取一次存档（`state #> '{}'` + `offset 0`），本机 2,261 → 620 ms、957k → 213k 页。冷启动第一次仍要等。
5. **`/api/admin/db`** 增加 `settings`（shared_buffers 等）、`activity`（当前各等待类型和最长时长）、`cache`（命中率），下次停顿时能直接看库在等什么。

## 复核两项 P2 的处理

1. **增量计数漏算迟提交**：确认（复现 11 行/上限 10）。改为只数到汇总水位 `foldedUpTo` 为止：rollup 前移水位前用 SHARE 锁等完所有在途插入，水位以下不会再有迟提交；水位以上的尾部每次现数、不入 memo。不传水位（只有测试会这样）时不用 memo、照旧走表。复现脚本现在 PASS。新增 `scripts/pg/check_prune_memo_pg.ts`：真实 PG 上 60 小时随机的迟提交、回滚空洞、水位落后、锚点过期、按天龄删除，每小时核对 memo 计数等于实数、表正好在上限；把 memo 改回“信最大可见编号”时 138 项失败（最后 512 行，上限 500）。PGlite 版 `scripts/check_prune_memo.ts` 进常规审计。
2. **冷实例 `ensureOpen` 绕过锁超时**：确认（5.8 秒）。报名时 `ensureOpen` 也在 `seatTx` 里跑（同样 3 秒），提交后才记 `known`；锁忙同样回「正在开赛」。`check_cup_join_pools.ts` 第二段改用全新 API 实例，两种杯赛都覆盖；把 `ensureOpen` 改回不受限时该测试失败。
3. 同 `at` 边界：一次走满 5 万行而游标没前进时，向前跳 1 微秒（只影响那一微秒里多余的行是否压缩，不影响正确性）。

## 已知边界

- memo 在进程内。部署交替的一两分钟里，如果旧实例的整点维护恰好跑了一次，新实例的 memo 会多数旧实例删掉的那批，下次会多删同样多的已汇总原始事件（约一小时量，汇总表不受影响），到每日重新走表时纠正。
- 前端加载（REPORT 第 4 节）没有在本轮改：没有实测数据，先看服务端修复后线上慢样本还剩多少。

## 上线后验收

- 日志：`analytics: history maintenance … ms` 每小时一行；`cards: request sweep took` 只有超过 1 秒才出现。
- 和 REPORT 同法采 HTTP ≥1 秒慢样本：:36 与 :x7 的簇应消失。
- 停顿时取 `/api/admin/db` 的 `activity`。
