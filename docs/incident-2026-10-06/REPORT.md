# 上线后响应慢：线上只读诊断

检查日期：2026-10-06。用户反馈：手机多个浏览器及电脑均有卡顿，涉及进入网站、杯赛、开包和“服务器没有回应”。本次没有改业务代码、生产配置、数据库或部署；只新增诊断材料。

结论：确有间歇性服务端慢请求。最强的共同原因线索是统计维护周期引发的数据库等待；另有已确认的杯赛报名与后台任务共用连接的问题。不能把所有反馈归结为手机性能，也不能用通常很快的接口分位否定用户体验。持续服务器 CPU 饱和或比赛计算积压，目前没有证据支持。

## 线上确认了什么

当前部署为 `3081b615-7a3c-4ffc-94dc-4bf14b93d1e4`，2026-10-05 17:33 UTC 创建。应用日志确认 17:35 启动，使用 4 个交互、1 个后台、2 个统计连接。17:39 完成 67,700 个账号的投影回填。健康端点确认运行版本指纹 `eb586a4e785a8dc126feb324ba72366a54ff844178896885155f014639daa22d`，数据库和 schema 就绪。

本次采集上线后约 13 小时内的 1,392 条大于等于 1 秒的慢请求记录。这是筛选后的慢样本，不能据此推算全站慢请求比例。

## 1. 首要排查：统计维护周期与跨页面卡顿高度重合

14 次统计清理完成日志中，13 次在每小时约第 36 分钟，另一次是启动后的第 3 分钟。1,392 条慢样本中，有 693 条落在这些完成时刻之前 20 秒至之后 5 秒的窗口。

- 2026-10-05 18:36 UTC，同一分钟有 89 条慢请求，涉及操作、市场、存档、登录和首页公告；最长 10.3 秒。统计清理在 18:36:08 完成。
- 2026-10-06 06:36 UTC，同一分钟有 75 条慢请求，涉及操作、存档、登录、榜单、市场和组队杯；最长 5.1 秒。统计清理在 06:36:08 完成。

代码对应关系：`server.js:228–229` 启动后 3 分钟维护，之后每小时维护；`history-maintenance.js` 先 rollup 后 prune。线上 `events` 约 300 万行、占 1,807 MB。`stats.js:581` 为保留行数上限执行 `ORDER BY id DESC OFFSET maxRows LIMIT 1`，默认 maxRows 为 300 万：即使有索引，仍需跳过大量条目，随后再删除旧数据。

另外，`rollup.js:150` 在每批汇总事务中锁 `events` 的 SHARE 锁，事件插入会等待；维护、事件写入和部分排行读取共用统计池。连接池分开不等于数据库的 CPU、磁盘和缓存也分开。

已确认：周期重合、查询形态、数据规模及共用资源。尚未确认：慢窗口里各 SQL 的具体锁等待/磁盘耗时；因此“维护导致数据库压力扩散”是最强原因假设，不能把时间重合作为完整因果证明。

优先修复方向：在隔离库按线上数据规模复现，拆出 rollup 和 prune 的耗时；改掉大 OFFSET 的保留策略，采用已汇总水位、安全时间边界或增量行数维护，处理序列空洞；维护改为小批、每批限时并让出资源。必须保留先汇总后删除和迟提交事件保护，不能直接删除 SHARE 锁或暂停统计后丢掉未汇总数据。若仍争抢明显，再评估统计独立数据库或合理分区，而不是只增加连接。

## 2. 已确认问题：杯赛报名使用唯一后台连接

`teamcup-api.js:102` 和 `opencup-api.js:164` 的通用 tx 使用 bg；报名和退出也使用这个 tx。`server.js` 将 bg 配为 sqlBg（默认 1 个连接），同池还承担市场结算、杯赛开赛/推进等后台工作。

线上存在直接对应证据：

- 2026-10-06 04:00:45 UTC 的组队杯报名请求，耗时 30,017 ms 后返回 500。
- 04:00:50 UTC 应用日志记录：`db: transaction gave up — bg: 等了 30 秒也没拿到数据库连接`。
- 性能接口确认 bg 的累计 gaveUp=1，main=0。日志时间与 HTTP 请求时间的字段语义不同，这里按相邻时段对应，不把时间戳差理解为另一段处理耗时。

这是等待取得后台连接，而非这一请求已经取得连接后做了 30 秒比赛计算。报名不应排在其他杯赛或市场后台任务后面。

修复方向：交互报名/退出用 sql 的短事务，后台推进继续用 bg；保留杯赛行锁、人数检查和重复报名幂等。ensureOpen 也需避免交互入口等待拥堵 bg。加回归：后台连接被占住时，仍能报名另一场尚未开赛的杯赛；同一杯赛正在开赛则按原锁规则安全处理。不能仅缩短客户端超时。

## 3. 仍有整份存档扫描，投影优化并未覆盖所有榜单

`cards-api.js:1218` 的上赛季榜和 `1272` 的预测榜仍遍历 card_accounts 的 JSON 字段，再在 Node 中排序/评分，缓存分别为 10 分钟与 5 分钟。这些路径不使用本轮新建的天梯/对手投影表。

对应端点的慢响应已经出现，但缺少 SQL 分段计时，尚不能确定具体一次是扫描本身慢还是等待统计连接。应使用榜单专用轻表/预计算、缓存后台刷新及 SQL 分段计时；不要让缓存到期的第一个玩家承担整表重建。

## 4. 前端和网络仍有待测成本，不能宣称已经定位全部体验问题

本次浏览器实际打开首页并进入卡池。在未登录状态已加载 world、dossier、Dossier、SeoulPackDisplay 等模块；当前 CardMode 仍静态导入 Packs、Collection、Squad、Challenge、Dossier。首页展示正常，无捕获到的浏览器报错，但这不是手机性能测试。

- 点击进入卡池或首次进入杯赛，仍可能等动态模块下载与解析。建议继续按页面拆包，并拆出展示用的轻量卡牌目录，避免登录页先加载模拟世界/资料库。
- `PackPouch` 首次挂载创建 WebGL、环境贴图、两张 1024×1536 纹理；货架和开包视图有多个实例。应测首包初始化及设备帧时间，考虑触屏静态货架/共享渲染资源。渲染器目前按需重绘，不能误报为持续无休止动画。
- `account.ts:82` 在操作回包后同步序列化并写入整份本地镜像；随后才触发页面更新。手机收藏很大时可能拖慢显示，需真实设备测量后决定合并/延后写入。
- 操作客户端一次等 25 秒，未知结果时同请求号重试一次，最多可等待约 51 秒；全服杯/组队杯读取没有显式超时。慢请求期间的反馈不足，会被描述为“没有回应”。调整反馈必须保留幂等和“结果未确认”状态，不能把超时说成没有扣款。

本地公网健康端点往返约 0.75 秒，而同次 readyz 数据库 ping 为 1 ms，说明端到端与内部耗时明显不同；这是当前检查位置的网络，不代表国内用户网络。电脑与手机都有反馈，所以不能仅凭设备类型判断根因。

## 当前不是这些问题的证据

已有性能快照：事件循环 P99 21 ms，整个进程记录的最大延迟约 179 ms；比赛 worker 完成 33,486 次，失败/拒绝均为 0、历史最大等待队列为 1。非重操作处理 P95 34.2 ms，杯赛模拟计算约 20～30 ms。最新交互连接等待 P95 近 0。

4 分钟粒度资源采样中，上线后的应用 CPU 最大约 0.17 vCPU；数据库最大样本是回填时约 1.76 vCPU，之后采样峰值约 0.11 vCPU。不能用平均采样排除短暂 I/O/锁尖峰，但不支持先靠升级机器或增加比赛 worker 解决。

## 下一步与验收

优先做“后台连接拥堵下的报名测试”和“300 万事件规模的维护与交互混合测试”，修复上述两个服务端路径；再补全请求读入、验证、SQL等待、回包压缩和浏览器下载/解析/本地写入/下一帧的分段计时。现有 action 计时从请求解析和手机号验证之后才开始，并在响应压缩前结束，尚非完整用户等待时间。

回归验收必须覆盖维护发生时的开包、登录、杯赛和市场 P95/P99，以及手机/电脑首次进入与热缓存操作，不能只检查最终数据一致或是否返回 200。上一轮上线建议基于一致性与功能回归，未完成这些端到端验收，不能用于证明这轮用户反馈已经解决。

生产采集为只读，未压测生产。直接 SSH 因未注册 SSH 密钥不可用，生产数据库未暴露公共 URL，未采到现场 pg_stat_activity/执行计划；没有为此新增权限或暴露数据库。已通过既有管理接口、Railway 日志及指标取得上述证据。原先 urllib 的 403 由后续 curl/浏览器正常访问排除，不能当作用户遇到的故障。
